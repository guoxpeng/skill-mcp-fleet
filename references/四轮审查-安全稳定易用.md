## 一、安全性：整体良好，2 个加固项

### 已确认无恙的部分（历轮加固 + 本轮复查）

| 检查项 | 结论 |
|--------|------|
| 文件路径穿越 | `_check_path` 用 `os.path.realpath`（解析软链），abspath 陷阱已规避；所有文件工具都过校验 |
| 鉴权覆盖 | `_guard()` 在 do_POST/do_GET 入口全覆盖；配 token 时 fleet 端点无旁路 |
| 配置文件权限 | `chmod 0o600`（mcp_agent 写配置、peers 注册表均覆盖）——auth_token/对端 token 不泄露给同机其他用户 |
| HTTP 请求体 | Content-Length 边界校验 + 1MB 上限（-1 读到 EOF / 超大值吃内存的坑已修） |
| SSE 资源 | 连接数上限 16（`max_sse_conns`），防打满线程 |
| exec 进程管理 | 独立进程组 + 超时杀整棵树（孤儿进程坑已修） |
| 常量时间比较 | `hmac.compare_digest` bytes 比较 |
| 工具层限流 | 令牌桶 `rate_limit_allow()`（每分钟 120 次可配），peer_call 场景覆盖 |

### S1（中危）：fleet/mail 端点不在限流范围内

- **现状**：`rate_limit_allow()` 只在工具层（peer_call）调用；`/fleet/mail` 收到消息直接 `inbox_append`，无限流、无容量上限
- **风险**：配 token 可防陌生人，但**已配对的失控节点（或 token 泄露）可无限塞消息**——1MB/条 × 无限次 = 磁盘耗尽（DoS）
- **修法**：fleet/mail 处理器加 `rate_limit_allow()` + inbox 容量上限（超出拒收并返回 503）。与 B10 是同一改动面，建议一起修

### S2（低危）：audit.log 无轮转

- **现状**：append-only 无轮转。每行 ~100B，按 1000 次/天估算 = 36MB/年，纯文本增速慢
- **修法**：超过 10MB 时轮转保留一份 `audit.log.1`（~5 行代码）
- **优先级**：低（比赛周期内无实际影响，常年挂机场景值得做）

## 二、BUG：1 个实锤（B10，本轮最重要发现）

### B10（高危，已实锤）：邮箱文件只增不减

**三个泄漏源**：
1. `inbox.jsonl`：`inbox_read` 读不移出（只推进 cursor），消息永久累积；`poll_for_agent` 移出仅服务远程拉取场景
2. `sent.jsonl`：投递成功的消息永久追加
3. `outbox.jsonl`：`dead` 消息（超 250 次重试）永久保留

**实测**（30 天 200 条/天场景）：
- 6000 条已读消息 → inbox.jsonl 0.9MB
- `inbox_read` 每次全量加载 + 逐条解密，6000 条时 10 次读取 0.8s——**线性变慢，消息越多越慢**

**为什么重要**：mcp-fleet 的目标设备是 NAS/软路由/办公室电脑——**常年不关机是常态**。挂机半年 = 数 MB 邮箱文件 + 每次读秒级延迟 + gossip/投递循环被拖慢。这是继 B5（死节点拖垮投递）之后又一"核心场景必然触发"的缺陷，且两者都指向同一个产品承诺：长期运行可靠性。

**修法（MailEngine.maintenance()）**：
- inbox：移出「所有 agent 已读（id < min(各 cursor)）且早于保留窗口」的消息，保留最近 N 条（默认 500）供 Dashboard 最近消息流展示
- sent / outbox-dead：截断保留最近 N 条（默认各 200）
- 触发：delivery_loop 低频执行（如每 3600s 一次），维护本身持锁原子写（复用 `_save_jsonl` 的加密回写路径，不引入 B1 类问题）
- Dashboard stats 增加 `inbox_bytes/dead_count` 字段，长期运行健康度可视化

## 四、易用性：1 个亮点项 + 已确认良好的部分

### U1（中，建议做）：doctor 不覆盖协议层

- **现状**：`fleet.py doctor` 的 6 项体检（TCP/HTTP/MCP/真实调用/mesh/health）都是"主端→副端"链路视角；v5.0 协议层（mailbox 状态/peer 熔断冷却/UDP 发现/gossip 同步）不在体检范围
- **痛点场景**：用户遇到"消息发不出去"→ doctor 全绿（链路健康）→ 实际是 peer 处于熔断冷却。诊断工具与故障现象脱节
- **修法**：doctor 追加第 7 项「协议层体检」——拉取 `/fleet/ui/data`（已有端点，零新增攻击面），展示 outbox_pending/inbox_total/dead 数/各 peer 的 cooldown；配合 stats() 扩展（B10 顺带）效果最佳
- **答辩价值**：演示"熔断 + 自愈"过程时有工具可看，技术叙事更完整

### 已确认良好的易用性设计（无需调整）

- 启动横幅信息完整：版本/监听地址/Dashboard 入口/无 token 醒目警告（`[!] 任何能访问本端口的人都等于拿到本机 shell`）
- `fleet.py` 子命令齐全（list/probe/doctor/exec/exec-async/health/bootstrap/tunnel 等 20+）
- 一条命令装机（install.py / install.sh 双通道）+ `--uninstall` 保留数据
- SKILL.md 触发词覆盖充分
